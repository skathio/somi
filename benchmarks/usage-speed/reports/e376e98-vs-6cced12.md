# Usage and speed evidence report: e376e98 against 6cced12

The `somi_loop` MCP tool: `/code-loop` and `/plan-loop` run each loop transition as one tool call instead of
about 21 shell and edit steps per pass. Pre-registered in [`loop-step-mcp-prereg.md`](./loop-step-mcp-prereg.md)
(metrics, the mechanism bar, and the two amendments naming this candidate, all committed before any of its rows
existed). Procedure: [`docs/USAGE-BENCHMARK.md`](../../../docs/USAGE-BENCHMARK.md).

**Result: inconclusive on cost, the primary metric, and the mechanism bar is missed.** On S1 (`/code-loop`) the
main thread fell from 164k to 117k weighted tokens (-29%) and from 24.5 to 16 turns, and the SoMi arm's median cost
from $0.046 to $0.036; the bar was 13 turns or fewer. S2 and S3 (`/ship-loop`) did not move. The quality guard is clear.

### Where the turns went (transcripts, not the rule)

Weighted token cost per agent (cache reads 0.1, cache writes 1.25, uncached input 1; output not in the per-message
usage the stream carries), medians per SoMi draw, baseline → candidate. The same script reproduces the 6cced12
report's figures from its transcripts.

| Scenario | Main thread | Coder | Reviewer |
|---|---|---|---|
| S1 (`/code-loop`) | 164k → 117k, 24.5 → 16 turns | 58k → 72k, 8 → 10.5 turns | 47k → 57k, 5.5 → 7.5 turns |
| S3 (`/ship-loop`, small) | 218k → 230k, 22 → 24 turns | 152k → 155k, 10.5 → 11 turns | 64k → 66k, 4 → 6 turns |

The S1 main-thread median is above the pre-registered 13 turns, so the mechanism did not work as designed. Where
the turns went, per S1 draw (main-thread turns: 15, 15, 15, 24, 24, 23, 16, 16):

- **Three of eight loops needed a second pass** (seeds 4, 5, 6; seed 5 stopped on the circuit breaker). A pass
  costs about 8 main-thread turns on the tool, so these draws land at 23–24. The five one-pass draws took 15–16.
- **Every draw wrote progress.md by hand after `close`.** The fixture's progress.md has no `**Last activity**`
  line, so `close` hands it back as `unwritten` (kind `last-activity`), and it does not update the phase table's
  done count (`0/1` → `1/1`). The main thread spent 3 to 7 tool calls (2 to 3 turns) on these two edits in all
  eight draws.
- **Getting to the first `open` takes 1–2 turns** (loading the skill, then the tool schema).
- The main thread made no loop CLI call in any of the eight draws. Two `somi_loop` results were refusals, both on
  `after-review`: a finding's `symbol` over 100 characters (seed 1) and a verdict outside the set (seed 5).

The coder and reviewer cost more per draw (the extra second passes), so the S1 saving on the main thread is
partly given back. On S3 the code loop is one step inside `/ship-loop`, whose sizing, brief and gate steps are
still shell and file work on the main thread (median 12 Bash calls). One S3 draw (seed 6) ran its whole loop
through the CLI fallback and never called the tool: 72 main-thread calls and 37 turns, the costliest draw. The
S2 draw scored 0/31 (seed 7) stopped at the small-tier gate after sizing and never reached a loop, a
`/ship-loop` behaviour this change does not touch.

## Limits

- Per release, not per commit: the result covers every change in the release together.
- The verdict is for the recorded model tier only; context-size effects transfer in direction, sizing and
  other behaviour effects do not.
- L0 is exact bytes injected, not tokens billed. L1 is one host fingerprint. Live L2 resolves only large
  changes (about 50% or more); smaller changes read inconclusive by design.
- Quality is a coarse non-inferiority flag only; no quality win or loss is declared.
- The `somi_loop` definition (2,805 bytes) loads with the tool list every session and is in no L0 scenario.
- The per-agent split and the turn accounting come from the transcripts, not from the rule; they explain the
  verdict and do not replace it. A two-pass loop is a property of the draw, not of the change, so the S1 median
  depends on how many draws need a second pass (3 of 8 here).
